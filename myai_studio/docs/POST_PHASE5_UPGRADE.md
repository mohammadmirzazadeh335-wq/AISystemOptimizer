# After Phase 5: Windows 11 readiness, debugging, and real file workflows

The five phases are closed and `v0.5.0-phase5` still marks the end of Phase 5.
This document covers the work that came **after** that tag: making the source
honest and safe on Windows 11, fixing defects found in the running app, and
adding three capabilities the product was missing.

Nothing in this document was compiled into an `.exe`. The user asked not to
package; this round is source-level and runtime-level verification only.

---

## 1. Windows 11: what could be verified here, and what could not

This machine is Debian Linux. It cannot boot Windows, has no Wine, and cannot
run a Windows binary. Any sentence of the form "it runs on Windows 11" would be
a guess, so it is not written anywhere in this repository. What *is* written is:

| Level | Meaning | Status |
| --- | --- | --- |
| **Rules** | Platform decisions are pure functions with tests that run on any OS | **Verified** — `tests/unit/test_windows_platform.py` (37 tests), `scripts/check_portability.py` (16/16 at the time; 17/17 after §9.2) |
| **Static compatibility** | No POSIX-only import or assumption on a Windows code path; paths, encodings, process flags and file names handled | **Verified by code review + tests** — see §2 |
| **Runtime on Windows 11** | The window opens, a reply streams, a file compiles and runs | **NOT RUN** — this host cannot execute it |

The last row is the only one that can turn "should run" into "runs". It is one
command on a real Windows 11 machine:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\windows11_smoke.ps1
```

What that script does, in order: checks the OS version and CPU architecture,
checks Python 3.11, creates a throwaway virtual environment, installs
`requirements.txt`, runs `scripts/check_portability.py`, runs the full test
suite, starts the real GUI with a temporary workspace (`python -m myai
--smoke`), greps the log for `app_booted`, and prints a PASS/FAIL table with a
non-zero exit code if anything failed. `-SkipTests` skips the suite; `-Python`
selects another interpreter.

### 1.1 Defects that would have broken the app on Windows

These were not hypothetical: each is a code path Windows actually takes, and
each now has a regression test that runs on Linux.

| # | Defect | Why it matters on Windows | Fix |
| --- | --- | --- | --- |
| 1 | `sys.executable` used as the Python interpreter | In a frozen build that is `MyAIStudio.exe`; Code Studio would relaunch the app instead of running the file | `python_executable()` returns `""` when frozen and asks the detected toolchain; `build_plan` raises "No Python interpreter" |
| 2 | `subprocess.Popen` without `creationflags` | Every compile/run flashes a console window | `creation_flags()` → `CREATE_NO_WINDOW` on Windows, `0` elsewhere |
| 3 | Compiler probes decoded with the locale code page | A compiler printing a non-UTF-8 character raised `UnicodeDecodeError`, which is *not* caught by `SubprocessError` and crashed detection | `decode_output()` tries UTF-8/BOM, the preferred encoding, cp1252, cp850 and Latin-1, and never raises |
| 4 | Only the first `python`/`python3` on PATH was probed | Windows ships a Store stub `python3.exe` that exists but prints nothing; Python was reported missing while `py` worked | `_find_working()` probes every candidate; `py` is added on all platforms |
| 5 | `.bat`/`.cmd` files had no toolchain | `CreateProcess` cannot execute a batch file directly | A `cmd` toolchain (`cmd /c file.bat`) exists on Windows only |
| 6 | Windows file-name rules were unchecked | `CON`, `NUL.txt`, `a:b`, `name.`, `name ` and paths over 259 characters hit devices, change silently, or fail mid-write | `filename_problem()` / `path_problem()` reject them on **every** platform, so a project moved to Windows behaves the same |
| 7 | Persian text in logs hit a code-page console | `UnicodeEncodeError` inside logging on a cp1252 terminal | `SafeStreamHandler` re-encodes with `errors="replace"` |
| 8 | `taskkill` was launched without flags | The kill helper itself opened a console window | The same `creationflags` are passed to the kill call |

## 2. Debugging: defects found in the running application

| Defect | Symptom | Cause | Fix and test |
| --- | --- | --- | --- |
| Attachments never reached the model | A file showed as a chip, the model answered as if nothing was attached | `_handle_send` passed only `text`; `ChatService.send` had no attachment parameter | Files are ingested on the worker thread, extracted, and appended to that user turn; `tests/unit/test_attachments.py::test_send_sends_the_file_text_and_keeps_chips` asserts the text inside the request body |
| Sending with a file lost the file | Same | Same | Same, plus a UI test that sends through the window and inspects the fake transport |
| Tab was trapped in the composer | Keyboard users could never reach Send or the toolbar | `QTextEdit.setTabChangesFocus(False)` | Set to `True`; `test_tab_never_leaves_the_window` presses Tab 40× and asserts focus never escapes the window |

| An attachment-only message could not be sent | Send stayed disabled with a valid file and no text | `_update_send_state` required text | A file alone is a valid message; the conversation is titled after the file |
| Settings advertised fake "Phase 2" locks | "Available in Phase 2" under two categories, with a dead API-key field | Placeholder pages shipped in Phase 1 and never replaced | AI page: real provider status + temperature slider that writes `ai.temperature`. ## 3. New: sending a file to the assistant

A file dropped on the composer (or chosen with 📎) now becomes data the model
receives, not a decoration.

1. **Validate** — 65 extensions covering text, code, `.docx`, `.pptx`, `.xlsx`,
   images and PDFs; 25 MB per file; up to 8 files per message (enforced by the composer).
2. **Copy** — into `<home>/attachments/<hash>_<name>`, so the message keeps
   working after the original is moved or deleted.
3. **Extract** — UTF-8/UTF-16/legacy code pages with replacement instead of
   failure, Office files through `zipfile` + `xml.etree`, image dimensions read
   from the header. No new dependency was added.
4. **Send** — one fenced block appended to that user turn, labelled as data not
   instructions, capped at 60 000 characters per file and 120 000 per message.
   The block states the file name, size and whether it was truncated.
5. **Persist** — a new `attachments` table (schema v4) linked to the message
   with `ON DELETE CASCADE`. Chips come back after a restart.
6. **Preview** — the chip's eye button opens the extracted text with a copy
   button; a binary or unreadable file explains itself instead of showing junk.

**Honest gaps, stated in the UI:** images and PDFs are recorded by name, size
and (for images) dimensions, but **no pixel or PDF text reaches the model** —
there is no OCR and no PDF parser in this build. The chip tooltip says exactly
that. Later turns see only the file names, so a long chat cannot flood the
context window.

## 4. New: the assistant creating files

Three tools join the registry (12 → 15). All go through the same JSON-schema
validation, availability gates and approval dialog as the existing tools.

| Tool | Risk | Behaviour |
| --- | --- | --- |
| `search_files` | read | Case-insensitive search in the open project, optional `*.py` glob, returns `path:line: text`; refuses an empty query and a missing project |
| `make_folder` | write | Creates nested folders; refuses `../` escapes, absolute paths and Windows-reserved names; never overwrites a file |
| `create_project` | write | Creates a real folder under `projects/`, refuses reserved/invalid names, and makes it the current Code Studio project |

`create_project` is the only file tool that works without an open project.
Nothing is created without the approval gate when the setting is on.

## 5. New: command palette (`Ctrl+Shift+P`)

Nineteen real actions: open any of the 13 pages, new chat, search
conversations, settings, cycle the theme, attach files, open the data folder.
Type to filter; ↑/↓ moves a **visible** selection (a property, not Qt focus, so
it appears even before the window is activated); Enter runs it; Esc closes.

## 7. Limits that remain

* **No Windows runtime evidence** from this host — §1 says so in the product
  documentation too, not only here.
* **No OCR / no PDF text** for attachments; the UI says it, the tests pin it.
* **No live OpenRouter call** was possible here (no key, network blocked); the
  provider path is covered by mocked transports and labelled as such.
* The 259-character path limit is checked before writing, but Windows long-path
  support (if enabled by policy) is not detected.
* Attachments are copied and never garbage-collected automatically; deleting a
  conversation removes its rows, but the files remain until the user cleans
  `attachments/`. This is documented rather than silently deleting user data.

## 9. Second round (latest): seven new agent tools, a Windows source gate, key hygiene

This is a second, separate round of work after `v0.5.0-post-phase5`. The user
asked for three things and no compilation: prove the Windows path is sound,
prove the API key is handled safely **without calling OpenRouter**, and add
exactly seven new agent capabilities. All three are below.

### 9.1 Seven new tools (15 → 22)

| Tool | Risk | What it actually does |
| --- | --- | --- |
| `project_map` | read | Walks the open project: file/folder counts, bytes and real line counts per language, the five largest files and the entry points it recognises. Gives the model structure before it reads anything. |
| `find_files` | read | Glob search (`**/*.py`, `*.md`) with sizes and modification times, newest first, capped and ordered deterministically. |
| `read_lines` | read | Numbered line range (`start`, `end`) from one file, 120 lines by default and 400 per call, so a 5 000-line file costs a window instead of the whole file. |
| `scan_todos` | read | Every `TODO` / `FIXME` / `HACK` / `XXX` / `BUG` marker with file, line and the comment text. |
| `diff_files` | read | Real unified diff between two project files, or an explicit "identical" answer. |
| `apply_patch` | **write** | Applies a unified diff with `@@` hunks to an existing file. All-or-nothing: if any hunk fails, nothing is written and the error says which hunk and why (`patch.context_mismatch`, `patch.ambiguous`). Line numbers may drift; context must match exactly. |
| `fetch_url` | **network** | Reads one public http(s) page through the same `WebService` path the Web Research page uses: URL validation, a 2 MB read cap, HTML-to-text. Refuses without the network permission. |

`apply_patch` is the reason `myai/services/patches.py` exists as a separate,
Qt-free module: the parser is unit-tested against hunks with shifted line
numbers, blank lines, trailing whitespace, missing files and ambiguous context,
and it can never write a half-applied file.

Approval behaviour is unchanged and still one dialog per risky call: `read`
tools run directly, `write`/`execute`/`network` tools go through the existing
approval gate and are refused when the setting is off. The agent page shows all
22 tools with their real availability reason.

### 9.2 Windows: a static gate that fails the build

`scripts/check_windows_static.py` parses every file under `myai/` with `ast` and
reports, with file and line:

| Rule | What it rejects |
| --- | --- |
| `posix-import` | top-level import of `fcntl`, `termios`, `pwd`, `grp`, `resource`, `pty`, `tty` … |
| `console-window` | `subprocess` calls without `creationflags` |
| `shell` | `shell=True` in any `subprocess` call |
| `encoding` | text-mode `open()` without `encoding=` |
| `posix-api` | unguarded `os.fork` / `os.killpg` / `signal.SIGKILL` |
| `frozen-interpreter` | `sys.executable` used as a child process command |
| `posix-path` | literal `/usr/`, `/bin/`, `/etc/` paths |

The scanner also fails on any file it cannot parse (`syntax`), so a broken file
cannot hide behind a green run. `tests/unit/test_windows_static.py` (13 tests)
feeds every rule a violating snippet and asserts it is caught, then asserts the
real `myai/` tree is clean — so the gate cannot go green by accident.
`scripts/check_portability.py` runs the scanner as its seventeenth check:
**17/17 passed** on this tree.

This does not prove Windows runs the app. It proves the source contains none of
the constructs that break it there. The runtime proof is still
`scripts/windows11_smoke.ps1` on a real Windows 11 machine, and it is still
**not run** here.

### 9.3 API key: proven sound without a live call

The user asked that the key not be tested live. So nothing here contacts
OpenRouter; every statement below is enforced by
`tests/unit/test_api_key_safety.py` (19 tests) and by code inspection.

| Property | How it is enforced |
| --- | --- |
| Wrong shape never leaves the machine | `openrouter.api_key_problem()` checks the `sk-or-` prefix, length (≤ 200) and the absence of whitespace, control characters and DEL **before** a request object is built. A transport stub asserts it was never called for each bad key. |
| No header injection | A key with `\r\n` or a space is rejected; it can never be spliced into `Authorization`. |
| Not echoed in errors | Every failure is an i18n key — `error.api_key_missing`, `api.key_format`, `api.key_too_long`, `api.key_invalid_chars` (the settings page maps the empty case to `api.key_empty`) — and the value is never interpolated. A test asserts a rejected key appears in neither the message nor `to_dict()`. |
| Not in logs | `core/redaction.py` masks `sk-or-*`, `sk-*`, `ghp_*`, `github_pat_*` and `Bearer …`; `RedactFilter` is installed on the file, console and inspector handlers, so even a mistaken `logger.info("…%s", key)` writes `sk-or-…abcd`. |
| Not on disk in clear | The store keeps an encrypted envelope (`secrets.bin` + `secret.key`, 0600; DPAPI on Windows). Tests scan `secrets.bin`, `secret.key`, every `*.db`/`*.sqlite`/`*.json` under the data folder and the backup archive for the key bytes: none found. |
| Not in backups or exports | Same test: the key appears in neither the zip nor the settings export. |

What is **not** proven: that a valid key actually authenticates — that needs a
live call, which the user reserved for themselves. The mocked provider tests
remain labelled mocked.
